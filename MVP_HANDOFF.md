# Supr-Mama MVP tracker

The single source of truth for V1 work. Every session (human or Claude) reads this first and updates it in the same commit as the work.

**How to use it**
- Work happens on `storefront-development`. Optionally use a short-lived branch per step and merge it back; remove the branch line from here once merged.
- Tick a box only after the change is on `storefront-development` **and** verified. Add the commit hash and one line saying how it was verified.
- New findings go under the step they belong to, as unchecked items. Don't keep them in chat or in separate notes files.
- Decisions go in **Decisions**, with a date. Open questions go in **Open questions** until decided.
- Items are numbered (`S2.3`). Reference the number in commit messages.

Legend: `[ ]` to do · `[~]` in progress · `[x]` done · **⛔ blocks** = must be finished before the item it names.

## Decisions
- **V1** (Oct 9): street-food **pickup and dine-in** orders, **paid online before the order reaches the vendor**. Delivery and Subscribe hidden behind a flag, not deleted.
  - Dine-in (decided Oct 9): **no note**. The customer only picks Pick Up or Dine In; table/spot details are sorted face to face or over a call. `dineInNote` was removed. Pay-first for both modes.
  - Vendor app shows Pickup vs Dine-in on each order card and on the order details screen.
- **V2:** self-delivery + simple daily subscriptions.
- **V3:** third-party delivery (Porter / Uber / Rapido). Check which of these actually offer an API in India before promising V3.
- **Payments** (Oct 9): online payment in V1 (UPI + cards). **Gateway is swappable** (decided Oct 10): one `PaymentGateway` adapter is active, chosen by `PAYMENT_GATEWAY`. **Razorpay chosen** (Oct 11: KYC submitted); Cashfree stays possible behind the same interface. Per-vendor payout accounts are gateway-specific, so switching gateways later means re-onboarding vendors.
  - Flow: server creates the order in `PAYMENT_PENDING` plus a Razorpay order → customer pays → server verifies the checkout signature **and** the `payment.captured` webhook → order becomes `PLACED` and only then shows in the vendor app.
  - Rejected or cancelled orders are refunded automatically via the Razorpay refund API.
  - Unpaid orders expire after ~15 minutes.
- **Time slots** (Oct 9): orders are for a 30-minute slot. The customer picks any slot after the current one, up to the **end of tomorrow by the calendar** (last slot tomorrow 11:30 PM; tonight's after-midnight slots count as tomorrow), inside the vendor's own opening hours. Hours are set **per weekday**; a day can be closed; closing may be **after midnight** (that tail belongs to the evening it started). A vendor with **no hours set gets no slots, so no orders**. All times are India time (Asia/Kolkata).
  - **Changed Oct 10:** hours are now **several slots per day, each inside the day** (latest close 12:00 midnight). Closing after midnight is gone: a 6 PM – 2 AM stall sets Mon 18:00–24:00 + Tue 00:00–02:00. Hours saved the old way were split automatically at startup (`HoursMigration`).
- **Vendor location** (Oct 10): the stall's point comes from the phone's GPS at the stall (search by area as a fallback, which only gives the area's centre); OpenStreetMap Nominatim names the place, through our API (free, ≤ 1 request/s, identifying User-Agent). The written address = shop/stall no. + landmark + area. Customers' "Directions" opens the exact point.
- **Storefront colours** (Oct 10): a fixed set of 8 light/dark pairs (`StoreThemes`: Sky, Mint, Peach, Lemon, Lilac, Rose, Sand, Stone); each pair passes 7:1 contrast for dark-on-light, white-on-dark and dark-on-white (tested). Free colour choice was removed.
- **Consumer home** (Oct 10): no public list of vendors. Later, customers use an app and scan vendor storefront QR codes; every vendor a customer opens is saved permanently on their home page. In the web launch customers only reach vendors through storefront links, so the home page just shows the vendors they opened.
- **Handover handshake** (Oct 10): an order is completed only when the party handing it over enters the customer's 4-digit code. The code is created when the vendor marks the order **Ready**; every order must pass through Ready. Lost code: support looks it up with `ops/handover-code.sh` after confirming the customer. Generic: vendor staff today, delivery partners for last-mile delivery later. The handing party never receives the code.
- **OTP delivery** (Oct 10): **WhatsApp only for the pilot** (no SMS, so no DLT registration). Same flow for customers and vendors. Our own `OtpService` stays the validator; only a new `WhatsAppOtpSender` is added behind the existing `OtpSender` interface (Meta WhatsApp Cloud API, Authentication-category template). An SMS fallback can be added later as a second sender without touching the validator. Anyone without WhatsApp can't sign in during the pilot; the Terms and the login hint say so.
- **Login code length** (Oct 10): **6 digits for vendor and customer login, not configurable.** Each new code resets the wrong-try counter, so the limits allow 25 guesses an hour (600 a day) on one number: ~6 % a day with 4 digits vs ~0.06 % with 6. The handover code stays 4 digits (it is shown in the app, not guessed remotely).
- **Handover vs OTP** (Oct 10): the handover code is **shown in the app** (customer status page) and entered by the handing party; it is never sent over WhatsApp. Only phone-number verification (customer and vendor login) goes over WhatsApp. They keep separate validators and share nothing: `HandoverRules` (4 digits, no expiry, lock after 5 wrong tries) vs `OtpService`/`OtpRules` (6 digits, hashed, 5-minute expiry, send limits).
- **Brand** (Oct 10): **Supr-Mama**, domain **suprmama.in** (registered). Code names (`in.foodcart` Java package, `foodcart` database, storage keys) stay as they are; only what people see changed.
- **Vendor accounts** (Oct 10): **one mobile number = one stall.**
  - **Changed Oct 11: vendors sign up themselves, the team approves.** Any number can log in to the vendor app; a new one gets a hidden draft stall and a setup checklist (stall name + link + colours, location, hours required; dishes and licence/payout details optional). The vendor submits; the team reviews with `ops/review-vendors.sh` (approve, or send back with a note). Customers can't see a stall until it is approved. `ops/create-vendor.sh` still makes a stall that is approved straight away.
- **Repository visibility** (Oct 10): make `amitranjan2/food-cart` **private** (owner does it in GitHub settings; see S4.10).
- **No cancelling after acceptance** (Oct 11): the vendor can reject a new order (full refund) but can't cancel one they have accepted. When a stall can't make an accepted order, **support refunds it by hand** after calling the stall (S3.7).
- **Main domain** (Oct 11): the **storefront owns `suprmama.in`** (store links and QR codes stay `suprmama.in/<stall>`); the website bought with the domain at Hostinger is not used for the root. Domain, DNS and the `tech@suprmama.in` mailbox stay at Hostinger: when pointing `suprmama.in` at the storefront host, change only the web records (A/CNAME) and keep the MX, SPF and DKIM records, or email stops.
- **Pricing** (Oct 11, S2.18): customer pays item prices (vendor's, before GST) + **GST on food 5%** + **platform charges 2.5%** of (items + GST), for online payment costs, + **18% GST on the platform charges**. All rates configurable (`FOOD_GST_PERCENT`, `PLATFORM_FEE_PERCENT`, `PLATFORM_FEE_GST_PERCENT`). **No cut of orders at launch**: the vendor gets the full item total. Main revenue: **vendor plans + 18% GST** (S4.24): **Daily ₹100** per day with at least one real paid order (not rejected/cancelled/refunded; team test numbers excluded), billed after each month; **Monthly ₹2,500** per calendar month, billed at its start; **Yearly ₹25,000** for 12 months, billed up front, locked for the term, renews. Every stall starts on Daily; a switch starts on the 1st of next month (or after a yearly term). Invoices due in 7 days, paid by UPI and marked by the team until payouts exist (decided Oct 11). A flat per-order fee may come later, only after traction. Delivery (V2) will add a delivery charge with its own GST.
- **Launch with pay at the stall** (Oct 11, S2.19): online payment is optional; the launch runs with `PAYMENT_GATEWAY=none` while Aks picks Razorpay Route or Cashfree split (S2.3). Cash bill = **items + 5% GST, no platform charges** (they cover online payment costs). The stall takes the GST in cash, but we owe it (s.9(5)), so it **passes it on monthly** on a GST statement due with the plan invoices. Guards: the stall marks **"Didn't come"** 30 min after the slot; **≤ 2 uncollected pay-at-stall orders** per customer at a time; **pay at the stall off after 2 no-shows** (support resets).
  - **Tax findings (checked Oct 11 against secondary sources; confirm with a CA):** GST on restaurant food sold through an app is paid by the **e-commerce operator (us)** at 5% under CGST Act s.9(5) (Notification 17/2021, from 1 Jan 2022; Circular 167/23/2021), in cash, even for unregistered stalls, and the operator issues the invoice for it ([ClearTax](https://cleartax.in/s/gst-on-notified-services-ecommerce-operators-95), [TaxGuru](https://taxguru.in/goods-and-service-tax/e-commerce-operators-liability-pay-gst-restaurant-services-wef-01-01-2021.html), [CBIC circular](https://cbic-gst.gov.in/pdf/Circular-167-17-12-2021-GST.pdf)). Our own charges (platform charges to customers, the daily charge to vendors) are our services at 18% ([CAclubindia](https://www.caclubindia.com/guide/gst-on-food-delivery-apps/)). An e-commerce operator **must register for GST whatever its turnover** (N6). Local delivery through an operator by unregistered riders: 18% under s.9(5) from 22 Sep 2025; a 57th-Council recommendation of 5% was not verified ([EY](https://www.ey.com/en_in/technical/alerts-hub/2025/09/cbic-issues-notifications-giving-effect-to-the-recommendations-made)). Income-tax TDS s.194-O: 0.1% of vendors' sales from 1 Oct 2024; not for individual/HUF vendors with ≤ ₹5 lakh sales a year who gave PAN ([ClearTax](https://cleartax.in/s/section-194o)). GST TCS (s.52) is not collected on s.9(5) supplies.
- **Branching** (Oct 9): `storefront-development` is the working branch.
